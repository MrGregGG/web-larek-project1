## Ограничения API

20.10.2026 прямое чтение официальной Postman-коллекции и каталога `/api/weblarek/product/` из среды проверки получило HTTP 503. Веб-инструмент также не смог открыть эти URL. Это фиксирует результат данной проверки, не устанавливает глобальную причину сбоя.

Origin подтверждён ТЗ, префиксы API/CDN — исходным `constants.ts`. `GET /product/`, `POST /order/`, поля DTO, `card/cash` и результат `{id, total}` документированы как проектные предположения по заданию HEAD. Фактический успешный ответ сервера не получен. Заказы не отправлялись. До подключения API в следующем спринте нужно сверить эти контракты с официальной коллекцией.

## Отчёт для HEAD

Окончательные решения:

1. MVP + исходный EventEmitter; один AppPresenter связывает модели, DOM и HTTP.
2. Три модели: CatalogModel хранит нормализованные товары, BasketModel — уникальные ID, OrderModel — поля покупателя. Сумма и счётчик не дублируются в заказе.
3. Нормализация `image → imageUrl` выполняется CatalogModel; числовые цены остаются числовыми, форматирование выполняется при подготовке View-данных.
4. LarekApi использует Api через композицию, проверяет внешние JSON-данные и не управляет состоянием магазина.
5. Три карточки имеют разные данные; общий механизм Form оправдан одинаковыми submit/validation/error, один Modal обслуживает все окна.
6. Для выбранного товара используется «Удалить из корзины». `null` означает запрет покупки, `0` остаётся допустимой ценой.
7. При каждом переходе с доставки к контактам поля контактов очищаются. Повтор отправки после серверной ошибки не запускает переход повторно и сохраняет поля.
8. Повторный HTTP-запрос и изменения заказа блокируются на время pending. Закрыть модальное окно можно; ответ обрабатывается независимо от него.
9. Успех: сохранить server total → очистить корзину/черновик → показать подтверждение. Ошибка: сохранить данные и показать текст. Автоматических повторов POST нет.
10. В этом спринте выполнены документация и типы; реализации классов намеренно отложены. Штатные HTML-шаблоны сохранены.

**Вопросов, блокирующих архитектурное решение HEAD, нет.** Проверка доступного API и получение отдельного чек-листа — оставшиеся внешние проверки, а не повод перепроектировать приложение. При расхождении настоящего API сначала корректируются DTO/адаптер; слои Model/View должны сохранить независимость.

Порядок следующего спринта: сверить API → реализовать и проверить модели → реализовать View поверх шаблонов → подключить AppPresenter → убрать демонстрационные окна → проверить сценарии покупки и ошибок. Публикация и отправка в GitHub в текущем задании не выполнялись.
